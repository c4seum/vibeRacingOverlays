# vibeRacingOverlays – notes for Claude

Standalone iRacing overlay app (C# / .NET 8 / WPF), an alternative to Kapps/RaceLab with **low FPS impact** as the main goal.
The user (c4seum) speaks **Dutch**: answer in Dutch. Setup: triple screens (3× 2560x1440, primary in the middle), no VR.

## Structure
- `src/vibeRacingOverlays.Data`: iRacing shared-memory reader (`IRSdk/`), lenient session-YAML parser, `DemoSource` (synthetic race), `RaceEngine` (positions, live gaps via 100 checkpoints/lap, relative, pit/tow/stint, iRating/SOF, fuel), `TelemetryService` (background thread).
- `src/vibeRacingOverlays.App`: WPF editor + overlay windows.
  - `Widgets/`: Standings, Relative, Fuel. Each is a `XxxSettings : WidgetSettings` with `[Setting]` attributes (the editor UI is generated from them) plus `XxxWidget.Draw(DisplayList, RaceSnapshot)`. Register new widgets in `Widget.Create`, `Widget.Catalog` and with `[JsonDerivedType]` on `WidgetSettings`.
  - `Rendering/`: widgets draw into a `DisplayList`. The window only redraws when the list changed (FPS!). `WpfRenderer` fits text inside its column (shrinks numbers, uses an ellipsis for names).
  - `Core/Settings.cs`: `AppSettings` holds Layouts (sets of widgets), Presets (per widget type), theme etc. Stored in `%APPDATA%\vibeRacingOverlays[-dev]\settings.json`.
  - `UI/`: settings panel with reset buttons (per setting / group / widget), live preview (live or demo single class / multiclass), side-by-side layout, `PositionPanel` (anchor/screen/offsets/lock of the selected widget + snapping; right of the settings when stacked, below the preview side by side). **Row heights are fixed**: every row in a card is `Ui.RowHeight` (34 px) with the control vertically centred, and every input control is `Ui.ControlHeight` (26 px: text box, combo, button, segmented, color swatch), so each row has the same 4 px of air above and below. Always create settings rows with `Ui.Row` (label | editor | reset), and rows with their own columns (like the column list) with `Ui.ListRow`. Never build rows as loose Grids, and never give rows or editors their own height or vertical margins. An editor that really can't fit (the 3×3 anchor grid) is marked with `Ui.MarkTall` (a UniformGrid counts as tall automatically). New settings via `[Setting]` go through `Ui.Row` automatically. Keep new UI consistent: build it from `UI/Ui.cs` (Card, Header + Reset, Row with dividers, Switch, Segmented, IconButton) and the styles in `App.xaml` (PrimaryButton for the one main action, GhostButton, IconButton); colors only via theme keys (`Themes/Dark.xaml` "Graphite", `Themes/Light.xaml` "Soft light", same keys in both). Never give a style the same key as a theme color (it overrides the brush and crashes).
  - `Overlay/Placement.cs`: widget position = screen ("Left/Middle/Right", same meaning on every PC) + 9-point anchor + inward offsets, in screen pixels; widgets grow away from their anchor. Snapping while dragging via `WM_MOVING` (snap distance / margin, Shift = free).
- Positions and lap times: iRacing's **session results** (`ResultsPositions` in the session info) are the reference; per-car telemetry (`CarIdxPosition`, `CarIdxBestLapTime`, `CarIdxLastLapTime`) is only filled for a few cars (the player and cars near the camera). Practice/qualifying: rank by the results (fastest lap); cars without a time after them by `CarNumberRaw` (iRacing's order; "012" = 3012 comes after "811"). Race: live/telemetry positions, results as fallback. iRacing doesn't provide other drivers' invalid lap times (LastTime -1). Check with `--dump` (cars table: telemetry vs results).
- `Data/Engine/RaceDistance.cs`: laps to go per iRacing rules (lap limit, time limit or both; overall leader ends the race, also multiclass; everyone finishes on the next line crossing). Pace = median of the last 5 clean laps per car.
- `src/vibeRacingOverlays.Setup`: .NET Framework 4.8 per-user installer (no admin rights). The app exe is embedded as a resource, plus a small uninstaller.
- `assets/logo.png`: the user's own "vRO" logo (transparent). `tools/make-icon.ps1` turns it into `src/vibeRacingOverlays.App/app.ico` (all sizes); rerun it after changing the logo.
- Docs: `README.md` is a **user guide** (features, widgets, installation, usage, FAQ), with no implementation details. Technical notes (dev build, releasing, structure, adding widgets) go in `DEVELOPMENT.md`. Keep both up to date when features change.

## Terms (user's wishes)
- In the UI they are called **widgets** (not overlays). The "Toggle overlay" button shows/hides all widgets.
- Single class vs multiclass is **detected automatically**. Class names/colors come from iRacing (`ClassNaming` recognizes GTP/LMP2/GT3... when iRacing leaves the name empty). No manual class editing.
- Renaming a widget only changes its display name; its type stays the same.
- Standings settings are split per session type (user's wish, 2026-10-01): **content** (rows, columns, header items, formats) per "Practice & qualifying" and "Race" (`StandingsProfile`, `ISessionProfiles`), **style** (colors, font, size, position, refresh) shared. Format options follow Kapps (the user sent screenshots): lap/gap decimals, license A3.48/A3.4/A3/A/SR, iRating 4567/4.5k/4k, temperatures °C/°F. Built into the existing settings cards, not a drag-and-drop pill bar.
- Pit status meaning depends on the session (user's wish, 2026-10-01): **TOW** only in a race, during iRacing's tow timeout after a reset (other cars: off the track / not in world without driving the pit lane, max 5 min; own car: `PlayerCarTowTime`). In practice/qualifying a reset is instant, not a tow. **PIT**: race = pit stop (orange badge, pit lane or box); P&Q = pit box is a grey "PIT" (between runs), orange only while driving in the pit lane. Number of stops only in a race. See `Widget.DrawPitStatus`.
- Layouts and presets (user's wish, 2026-10-02): **layouts and their widgets are always work versions** (autosaved; the layout selected in the sidebar list is the active one). All preset work is in the **menu bar** (`MainWindow.BuildLayoutMenu` / `BuildWidgetMenu`, rebuilt each time a menu opens), not in the sidebar or widget card. Layout menu: New empty / **New layout from preset** (a layout preset is **only loaded into a new layout**, never over an existing one), Rename, Delete, Save as preset, Save to preset, Manage presets, Export / Import layout. Widget menu (selected widget; `UI/WidgetPresets.cs`): Load preset (overwrites the widget's settings), Save as / Save to preset (asks to update other widgets using it; work layouts only), Manage presets, Export / Import preset. Built-ins **Get started** (`LayoutPreset.IsBuiltIn`, refreshed from `Defaults.StartLayout`) and the **Default** widget presets are read-only. **Get started as a work layout (user's wish, 2026-10-02):** a fresh install has only that layout; on the first start of another version (`SavedByVersion` differs) a layout named "Get started" is added when none exists (by name; a renamed one counts as missing), not made active, with a status bar notice (`AppSettings.EnsureStartLayout`). An existing one is never touched (it may be the user's work version). Deleting it sets `StartLayoutDeclined`, then updates don't add it again. Positions of Get started: Standings top left, Relative bottom right, Fuel bottom left, all 10/10 on the main screen (confirmed by the user). Add / Duplicate / Remove stay below the widget list. No "based on preset" shown (user's choice). A widget added with Add starts at anchor Center 0/0 on the main screen. Menus: no screenshots via screen capture (it catches the user's other windows); read menu items via UIA instead.
- Export / import (user's wish, 2026-10-01): a layout file holds each widget's own **current** settings, never presets (the widget's work version is the truth, presets are snapshots); on import a widget links to an identical preset of the user, else to their Default (`AppSettings.PrepareImported`). Preset files (`.vropreset.json`, name + settings, no position) via the *Preset file* row, drag and drop on the window, and the preset library `Documents\vibeRacingOverlays\presets` (`Core/PresetLibrary.cs`: mirrors every non-Default preset, takes in new/changed files also while running, rewrites files deleted outside the app). With `--settings-dir` the library is `<dir>\library`.
- Built-in defaults: the Default widget presets are `app/defaults/presets/*.vropreset.json` (embedded; the user's preferred settings, taken from `vibeRacingOverlays\vRO defaults` on 2026-10-02); Default presets are reset to them on every load and can't be saved over, renamed or deleted.
- **Widget changes in a release vs existing settings (user's decision, 2026-10-02): an update never changes how existing widgets, widget presets, layout presets or exported files look or behave.** A new option gets, for everything that already exists, the value that keeps the old behaviour (a new column / header item / symbol: off; a new setting for something that existed: the old value, e.g. a fixed 4 px gap becoming a setting = 4). Fresh installs and the **Default** presets get the recommended value. Only what you deliberately mark per release reaches existing users (a written migration). Communication: **release notes only** (no in-app "what's new" prompt). How to do it: see DEVELOPMENT.md, "Changing a widget". Still to build when first needed: inserting new columns next to a logical neighbour instead of at the end, a settings version number with numbered migration steps, and test files of earlier releases that every build loads.
- **Widget fonts** (user's choice, 2026-10-03, from a browser comparison of open-license race/gaming fonts and real renders): `WidgetSettings.Font` (Text & size > Font, enum `Rendering.WidgetFont`): Bahnschrift (default, existing widgets and Default presets keep it), Rajdhani, Titillium Web, Chakra Petch, Exo 2, Oxanium, Orbitron, JetBrains Mono, and (second round, 2026-10-04) Tomorrow, Bai Jamjuree, IBM Plex Sans Condensed, Sofia Sans Semi Condensed, Lexend, Jura. All but Bahnschrift are bundled as WPF resources in `src/vibeRacingOverlays.App/Fonts` (regular + semibold TTF from Google Fonts; JetBrains Mono from JetBrains' own repo, its semibold file is the family "JetBrains Mono SemiBold"; IBM Plex Sans Condensed likewise: always check a new font for WPF bold simulation), licences in `Fonts/FONT-LICENSES.txt` (also copied into the portable zip). `Rendering/FontCatalog.cs` maps names to typefaces. Widgets draw via `Widget.Paint` (measures in the widget's font through `TextMeasure.Use`, sets `DisplayList.Font` for the renderer). Layouts that place things at fixed widths must measure their content in the font (the Fuel calculator's columns grow for wide fonts). Compare fonts with `--font-samples`. Text is placed on whole pixels (`TabularText.Snap`). Text weight (Text & size > Text weight, `TextWeight`, default Semibold = old look): Regular maps the "bold" text to the regular face (font key "Name|regular", `FontCatalog.Key`). Investigated 2026-10-04 why fonts looked better in the browser picker: the preview used ClearType (fixed), and WPF draws semibold visibly heavier than Chrome (stroke about 1/4 vs 1/6 of the digit height); ClearType, Ideal mode and drawing as geometry were tried, Regular weight matched the browser best.
- **Settings cards** (user's wish, 2026-10-04): every widget has the same card order, set by `[Setting(Group = ...)]` and `SettingsPanel.GroupRank`: the widget card (Display name + group "Widget": Show, Refresh rate, at the top on the user's choice), "Content" / "Rows" / "Rows (single class)" / "Rows (multiclass)" / "Estimates", "Columns" and "Header bar" (list cards; settings of that group, like Column titles row and Show header bar, sit on top of the list), "Text & size" (Font, Text weight, Font size, Row height, Column spacing, Scale), "Colors" (Background opacity first, widget-specific colours after). Put new settings in one of these groups.
- **Every column (also new ones) must be neatly aligned**: digits are equal-width (`TabularText`), numbers right-aligned, and a format must never make values in one column differ in width except by their number of digits. Column widths are **fixed and computed** (`ColumnDef.Fit(sample)`: the widest content per format, measured at the font size, plus the column title when shown); only the driver name is user-sized (`UserWidth()`). Space between columns = the widget's "Column spacing". Give every new column a `Fit` sample. In the column list the move buttons come first, then the check box.

## Build / test / release
- Local test version: `.\publish-dev.ps1` produces a **DEV build** ("vibeRacingOverlays DEV", orange title, settings in `%APPDATA%\vibeRacingOverlays-dev`, Start menu "vibeRacingOverlays DEV"). Close the app first.
- Design checks without iRacing: `vibeRacingOverlays.exe --snapshot <folder>` (PNG per widget, demo single and multi, race and practice (`_pq`), plus the user's saved widgets and a narrow-columns test). `--snapshot <folder> --live` uses live iRacing data. `--dump <file>` writes raw iRacing values.
- Release: `.\build-release.ps1 -Version x.y.z` locally, or push a tag `vX.Y.Z` so GitHub Actions (`release.yml`) builds the installer and portable zip and creates a GitHub Release (notes = the version's CHANGELOG section). Before tagging: move Unreleased to the new version in CHANGELOG.md, add the version to the release history below, commit, push, then tag. **Never push a version tag without the user's explicit consent.**
- `gh` for this repo: `--repo c4seum/vibeRacingOverlays` (on the work laptop both accounts are logged in; see memory).
- Versions: last digit = fixes only, middle digit = new features.
- A normal `git push` only runs the "Build" check (`build.yml`); only a pushed `vX.Y.Z` tag creates a release.

## Working rules
- **Sandbox: my commands and the processes I start see their own copy of files they write** (an overlay over the real files; discovered 2026-10-02). What I read may not be the user's real file, and an app I start runs on those copies (that's how the user's presets seemed lost: the DEV app I restarted saw an old copy). So: start the user's DEV app **outside the sandbox** (`dangerouslyDisableSandbox`), and check the user's real files outside the sandbox. Test instances stay inside, with `--settings-dir`.
- **Never write the user's `settings.json`** (not even "backup and restore": on 2026-10-01 that lost the user's presets). UI tests run the app with `--settings-dir <scratch folder>` on a copy of the settings; the real file is only read. Close test instances (also leftover Debug instances).
- Settings safety net (2026-10-01): the app keeps `backups\` (one per day for 7 days, one before the first save of a new version, unreadable files), reads widgets/presets one by one (unknown ones are kept in `Unreadable` and put back later), logs save errors in `errors.log` and shows them red in the status bar. Keep it that way: settings changes must load old files, and nothing may silently fall back to defaults.
- Building the DEV version while the user's DEV app is open: the user allows closing it (2026-10-01), **on condition that it is started again afterwards**. Since the tray icon (2026-10-03) `publish-dev.ps1` does this itself: it asks a running `publish\vibeRacingOverlays.exe` to exit through its exit event (`CloseMainWindow` only hides it to the tray now), builds, and starts it again. Run it outside the sandbox. Only that DEV app; never other programs, and never the installed release version.
- Undo (user's wish, 2026-10-03; `MainWindow.Undo.cs`): buttons ↶ ↷ right after the Layout/Widget menus, Ctrl+Z / Ctrl+Y (not while a text box has focus). **Every change is tracked** (user's wish): the whole settings state (layouts, widgets, presets, layout presets, app settings) as JSON is compared every 300 ms while the window is visible or edit mode is on; a change becomes a step after 700 ms of quiet, so new settings and new UI are covered automatically without hooking controls. One global history (50 steps, not saved); undoing a change in another layout switches to it. Restoring keeps unchanged layout/widget objects (and their windows), mirrors the preset library (deleted presets lose their file). Not tracked (`NotTracked`): active layout, show/hide all, editor layout, bookkeeping fields. A new AppSettings field is tracked automatically; add it to `NotTracked` if it's view state, and give it a side effect in `ApplyState` if changing it needs one (like theme, data source, font).
- Staying on top (2026-10-03, after the user saw widgets over the taskbar, menus and the Win+Shift+S screen): widgets are topmost windows; they are only lifted again (`OverlayWindow.BringToTop`) while **iRacing is the foreground window**, not in exclusive full screen, and only when a window of another program overlaps them (`CoveringWindow`; other copies of this app don't count). The user runs iRacing as a window without border (`rendererDX11Monitor.ini`: fullScreen=0, border=0, 7680x1440 at -2560,0). Full screen (fullScreen=1) gives a status bar warning (`IRacingWindow.BlocksWidgets`). Not yet checked with iRacing running: use `--zorder-log`. Never log window titles of other programs.
- Hotkeys and wheel buttons (user's choice, 2026-10-04: configurable keys + wheel / button box buttons; actions previous layout, layout 1-4, widget 1-5, fuel custom ±0.05, fuel averages reset). `Core/Hotkeys.cs` (actions, `AppSettings.Hotkeys`, migrated from the old HotkeyEditMode strings), `UI/HotkeysWindow.cs` (Hotkeys menu; actions are suspended while it's open), `OverlayManager.Do/ReloadHotkeys` (RegisterHotKey ids 100+catalog index; failures shown red as "in use"), `Overlay/ControllerInput.cs` (Raw Input with RIDEV_INPUTSINK on its own thread and message-only window, HidP_GetUsages for buttons; only runs while a button is bound or being captured; devices by VID/PID). New actions have no default keys on purpose (global hotkeys steal combinations from other programs). Test hotkeys by posting WM_HOTKEY to the app's own window, never by sending keystrokes. Not yet tested with a real wheel.
- Tray and single instance (2026-10-03): closing the main window hides the app to the tray (`AppSettings.CloseToTray`); Exit is in the tray menu. One app per settings folder (named mutex); a second start shows the running window. To stop an app from a script, set `Local\vibeRacingOverlays-exit-<pid>`. Test instances: `--settings-dir`, then kill them.
- UI Automation: toggle buttons/checkboxes react to Checked/Unchecked (a UIA Toggle doesn't raise Click); find windows by the test process id.
- Never send keystrokes blindly: the user's other windows are often in front. Use UI Automation, the `--silent` installer mode, or PrintWindow for screenshots.
- `winget`-installed tools (dotnet, git, gh) may be missing from PATH in already-open terminals: refresh with
  `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`.

## Working on several PCs
- The user works on a home PC (with iRacing) and a work laptop (probably without iRacing: develop with the demo race, test in-game at home).
- Start a session with `git pull`, end it with `git push`.
- Layouts/presets/settings are not in git: use Export / Import (layout or widget files), or copy `%APPDATA%\vibeRacingOverlays-dev\settings.json` between PCs.
- New PC setup: `winget install` Git.Git, GitHub.cli and Microsoft.DotNet.SDK.8, restart the Claude app, run `gh auth login` and `gh auth setup-git`, `git clone https://github.com/c4seum/vibeRacingOverlays.git`, then `.\publish-dev.ps1`.
